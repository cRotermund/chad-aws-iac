# ADR 001: Use SSM Parameter Store for Secrets Management

- **Status:** Accepted
- **Date:** 2025-07

## Context

The K3s cluster requires several secrets during provisioning and operation:

- Cluster join token (generated by Terraform, needed by EC2 instances at boot)
- Kubeconfig (generated by the server, needed by Terraform for outputs)
- ArgoCD initial admin password (generated by ArgoCD, needed by operators)

These secrets must be shared between Terraform (provisioning time) and EC2 instances (boot time), and must be retrievable by operators after deployment.

## Decision

Use **AWS Systems Manager Parameter Store** with `SecureString` type for all secrets.

Terraform creates placeholder parameters during `apply`, EC2 instances read/write them via IAM instance profiles at boot, and Terraform reads them back as outputs.

### Alternatives Considered

| Option | Pros | Cons |
|--------|------|------|
| **SSM Parameter Store** (chosen) | Encrypted at rest; no additional cost; native IAM integration; Terraform data source support | AWS-only; parameter hierarchy needs planning |
| AWS Secrets Manager | Automatic rotation; cross-account support | Paid service; overkill for static tokens |
| HashiCorp Vault | Platform-agnostic; rich secret engine | Requires its own infrastructure; complex to bootstrap |
| Pass via user_data directly | Simple | Secrets exposed in EC2 console/API; Terraform state does not track |
| Manual provisioning | No automation needed | Error-prone; requires SSH access before cluster forms |

## Consequences

- **Positive:** Secrets are encrypted at rest and never appear in user_data or Terraform outputs unmasked
- **Positive:** EC2 instances self-configure at boot via IAM role — no manual intervention needed
- **Positive:** Terraform can read kubeconfig and ArgoCD password as outputs immediately after `apply`
- **Negative:** Terraform state contains the secret ARNs; the S3 state backend must be secured
- **Negative:** Token rotation requires a `terraform apply` with tainted resources
